# AGENTS.md

## Область действия и границы

Инструкции действуют на весь репозиторий. Рабочие области: `src/server`,
`src/client`, `src/extension`, `docs` и связанные корневые конфигурации.

Не изменяйте без прямой необходимости `.git`, секреты и локальные файлы (`.env`,
fingerprints, базы), зависимости и generated output (`node_modules`, `build`,
`.svelte-kit`, `.wxt`, `.output`, Tauri resource build). Lock-файлы меняются
только вместе с осознанным изменением зависимостей. Примененные Alembic-миграции
не редактируются — создается новая миграция. Не затрагивайте несвязанные с
задачей компоненты и пользовательские незакоммиченные изменения.

## Архитектура и код

- Соблюдайте DRY, SOLID, KISS и YAGNI прагматично: предпочитайте ясный небольшой
  код и не создавайте абстракцию до появления устойчивой границы.
- Доменная и бизнес-логика зависит от собственных типов и интерфейсов, а не от
  FastAPI, SQLAlchemy, Tauri, browser API, SDK и конкретных внешних клиентов.
- Явные реализации сторонних систем размещайте в adapters/infrastructure;
  подключайте их в composition root через dependency injection.
- Валидируйте и преобразуйте внешние данные на границе. Не протаскивайте модели
  провайдера, transport DTO или ORM-модели в бизнес-правила.
- Разделяйте UI, состояние, побочные эффекты и чистые правила. Не скрывайте
  сетевые, файловые или database side effects в доменных функциях.
- Изменение поведения сопровождайте тестом; исправление дефекта — regression
  test. Не ослабляйте типы, линтеры и проверки ради прохождения сборки.

Подробные границы компонентов определены в `docs/architecture.md` и должны
оставаться согласованными с кодом.

## Документация

Документация — часть каждого изменения. Обновляйте соответствующий файл в
`docs/` одновременно с кодом: текущее состояние, архитектуру, команды,
аутентификацию, данные или развертывание. Значимые и долгоживущие архитектурные
решения оформляйте отдельным ADR по `docs/adr/template.md`; не превращайте README
в журнал решений.

Пишите стандартный Markdown с относительными ссылками, одним H1 и Mermaid для
схем. Отделяйте текущее состояние от планов, не указывайте секреты и не сохраняйте
быстро устаревающие числа без даты и источника.

### Технические задания

Если пользователь явно просит написать, составить или оформить техническое
задание по его требованиям, сохраните окончательную редакцию в `docs/tasks/` по
правилам из `docs/tasks/README.md`. Используйте следующий свободный номер,
шаблон `docs/tasks/template.md` и укажите актуальный статус. Промежуточные
варианты сохранять не нужно.

Этот workflow применяется только к явному запросу на подготовку ТЗ. Обычные
запросы на реализацию, исправление, исследование, ревью или объяснение сами по
себе не требуют создания файла в `docs/tasks/`.

## Проверки

Для каждого затронутого компонента перед завершением запустите formatter check,
linter, type checker, тесты и build, перечисленные в `docs/development.md`. Для
Rust обязательны `cargo fmt`, `clippy`, `test` и `check`. Для Python минимум —
`compileall` и `pytest`; отсутствие настроенных formatter/linter/type checker
нужно явно сообщить, а не считать успешной проверкой.

В отчете перечислите выполненные команды и результат. Если проверка недоступна
или неприменима, укажите это явно вместе с причиной.
