# Ascend Trenches — ТЗ/спецификация (Server + Desktop Client)

Версия: 0.1  
Статус: черновик (для уточнений и последующей разработки)  
Область: `src/` (и сервер, и клиент)

## 1) Контекст и цель проекта

Нужно построить систему, где:

- **Сервер** принимает/собирает поток событий (token feed) из одного или нескольких источников, затем **стримит их по WSS** авторизованным клиентам.
- **Клиент (desktop, кроссплатформенный)** подключается по WSS, **фильтрует события локально** по настройкам пользователя, и при совпадении условий **может автоматически открывать ссылки** в браузере.
- **Авторизация** на первом этапе — по **API ключам** (license keys). В будущем допускается развитие в сторону пользователей/организаций без ломки текущего API/WSS контракта.

Текущий код, который важно **сохранить концептуально**:

- `src/server/app/services/token_feed/token_feed_preparer.py` — протокол `TokenFeedPreparer`
- `src/server/app/services/token_feed/collector.py` — `TokenFeedCollector`, который принимает список `TokenFeedPreparer` и агрегирует события
- `src/server/app/services/token_feed/axiom_dev_token_data.py` — пример источника (Axiom) как preparer
- `src/server/app/schemas/token_feed_models.py` — Pydantic модели `TokenFeedBase`, `DeployedToken`

## 2) Высокоуровневая архитектура (без привязки к конкретной реализации)

### 2.1 Компоненты

- **Feed Sources (Collectors/Preparers)**: набор “адаптеров” к внешним источникам (например, `axiom_trade_api`, позже `gmgn_api`), каждый приводит входной payload к единому формату `TokenFeedBase`.
- **Feed Aggregator**: агрегатор, который принимает события от источников и публикует их дальше (внутренняя шина / очередь / брокер).
- **API сервис**:
  - управление ключами (админка),
  - авторизация,
  - выдача конфигурации клиенту,
  - метрики/статусы,
  - WSS endpoint для подписки на поток.
- **Desktop клиент**:
  - активация ключа,
  - подключение по WSS,
  - фильтрация + автооткрытие ссылок,
  - локальные настройки и UI.

### 2.2 Данные и поток обработки

1) Внешний источник (например Axiom websocket) отдаёт raw events.  
2) Конкретный preparer превращает raw event → `TokenFeedBase` (или `None`, если событие не подходит).  
3) Aggregator публикует `TokenFeedBase` в stream.  
4) WSS сервер доставляет события авторизованным клиентам.  
5) Клиент фильтрует локально и при необходимости открывает ссылку.

## 3) Стек (рекомендуемый)

### 3.1 Backend

- **FastAPI + Uvicorn** (уже используется)
- **PostgreSQL** — постоянное хранение ключей, политик, аудит-логов
- **SQLAlchemy 2.0 / SQLModel + Alembic** — модели и миграции
- **Redis** — rate limiting, хранение активных WSS-сессий/лимитов, pub/sub для рассылки (если будет несколько воркеров)
- (Опционально по росту нагрузки) **NATS/RabbitMQ** — брокер событий между источниками и WSS
- **Docker Compose** — локальная разработка (api + postgres + redis)

### 3.2 Desktop клиент (кроссплатформенный)

Рекомендуемый вариант:

- **Tauri** + UI на **React** (или Vue/Svelte)
  - лёгкий runtime по сравнению с Electron
  - удобный UI как веб
  - безопасный доступ к системным функциям (в т.ч. открытие ссылок)

Альтернативы:

- **Electron** (проще стартовать, но тяжелее по ресурсам)
- “Всё на Python” для desktop (возможны варианты), но обычно сложнее обеспечить кроссплатформенность и хороший UX именно для desktop-приложения с системными интеграциями.

## 4) Требования к безопасности (включая anti-bruteforce и ограничение подключений)

### 4.1 Общие требования

- Только **HTTPS/WSS (TLS)** на проде.
- Ключи в БД хранить **только в виде хэша** (никогда не хранить “сырой” ключ).
- Ключ показывается пользователю **только один раз** при создании.

### 4.2 Защита от брутфорса/частых подключений

Требования:

- **Rate limit на API**:
  - на IP (например, `/auth/validate`, `/ws` handshake, админ-эндпоинты),
  - на ключ (если ключ уже известен/валиден),
  - на “ошибочные попытки” (невалидный ключ).
- **Rate limit на WSS подключения**:
  - ограничение частоты реконнектов на IP и/или key_id,
  - лимит одновременных активных соединений на ключ (см. политику ключа).
- **Fail2ban-подобная логика**:
  - при \(N\) неуспешных попытках за окно времени → временный бан IP/подсети на \(T\) минут.
- Сервер должен возвращать клиенту **понятную причину** (код/текст) при отказе: “invalid key”, “expired”, “rate limited”, “revoked”, “too many sessions”.

Реализация (принципиально, без кода):

- Redis как хранилище счетчиков: `rl:ip:<ip>`, `rl:key:<kid>`, `rl:fail:<ip>`
- Нормы (пример для обсуждения, фиксируются при внедрении):
  - validate key: 10 запросов/мин на IP
  - ws connect attempts: 6/мин на IP
  - failed auth: 10/10 мин → ban 30 мин

## 5) Авторизация и модель лицензирования по API ключам

### 5.1 Сущности (минимальный набор)

- **ApiKey**
  - `id` / `kid` (публичный идентификатор)
  - `key_hash`
  - `label` (метка)
  - `status`: active | revoked
  - `created_at`
  - `expires_at`
  - `max_active_sessions` (лимит одновременных подключений)
  - (опц.) `max_devices` (если различать устройства)
  - (опц.) `metadata` (json)

- **ApiKeySession** (можно держать в Redis, а в БД только аудит)
  - `session_id`
  - `api_key_id`
  - `connected_at`
  - `last_seen_at`
  - `client_fingerprint` (опционально)
  - `ip`
  - `user_agent/app_version`

### 5.2 Поведение при истечении/отзыве

- Если `expires_at` наступил:
  - WSS соединение закрывается сервером немедленно (или при ближайшей проверке keepalive), клиент получает “ключ истёк”.
- Если ключ отозван:
  - аналогично истечению, но причина “revoked”.

### 5.3 Расширяемость на пользователей

Сразу закладывается возможность добавить сущности:

- `User`
- `Organization/Workspace`
- связи: org → keys, user → org

При этом **контракт WSS “ключ → доступ” сохраняется**, а в будущем может появиться второй способ (JWT/OAuth), не ломая текущих клиентов.

## 6) API (HTTP) — минимальный контракт

Ниже — рекомендуемый контракт. Конкретные пути можно адаптировать.

### 6.1 Публичные (для клиента)

- `POST /api/v1/auth/validate-key`
  - вход: ключ (Bearer или `X-API-Key`)
  - выход: статус (valid/expired/revoked/rate_limited), оставшееся время, лимиты

- `GET /api/v1/client/config`
  - отдаёт клиенту “фичи”/параметры по умолчанию, версии протокола

### 6.2 Админские (управление ключами)

Доступ защищается отдельной админ-авторизацией (минимум — admin API key, позже — пользователи/роли).

- `POST /api/v1/admin/keys` — создать ключ (expires_at, лимиты, label)
- `GET /api/v1/admin/keys` — список ключей
- `PATCH /api/v1/admin/keys/{kid}` — изменить политику/срок
- `POST /api/v1/admin/keys/{kid}/revoke` — отозвать
- `GET /api/v1/admin/keys/{kid}/sessions` — активные сессии
- `POST /api/v1/admin/keys/{kid}/kick` — отключить активные сессии (все или выборочно)

## 7) WSS протокол (сервер ↔ клиент)

### 7.1 Подключение и авторизация

Варианты (выбрать 1 и зафиксировать):

1) **Query param**: `wss://host/ws?api_key=...` (проще, но хуже с точки зрения утечек в логах)
2) **Header**: `Authorization: Bearer <api_key>` (предпочтительно)
3) **Первое сообщение**: клиент подключается, затем отправляет `{"type":"auth","api_key":"..."}` (удобно для некоторых WSS клиентов)

Рекомендуется вариант 2 или 3.

### 7.2 Формат сообщений

#### Событие token feed

- `type`: `"token_feed"`
- `payload`: объект формата `TokenFeedBase` (как в `src/server/app/schemas/token_feed_models.py`)
- (опц.) `source`: `"axiom"` | `"gmgn"` | ...
- (опц.) `ts`: timestamp сервера

#### Системные сообщения

- `"error"`: причина отказа/закрытия (invalid_key/expired/revoked/rate_limited/too_many_sessions)
- `"ping"` / `"pong"` или keepalive по стандартным средствам WSS

### 7.3 Закрытие соединения при истечении ключа

Требование:

- Сервер обязан закрыть соединение и отправить причину так, чтобы клиент мог показать понятное сообщение:
  - “Ключ истёк”
  - “Ключ отозван”
  - “Слишком много одновременных подключений”
  - “Слишком частые подключения”

## 8) Desktop client — требования

### 8.1 Активация ключа

- UI: поле ввода ключа, кнопка “Активировать”.
- При успешной проверке — сохраняет ключ локально (желательно в системном secure storage).
- При неуспешной — показывает причину (expired/revoked/invalid/rate_limited).

### 8.2 Подключение и устойчивость

- Автоподключение на старте.
- Реконнект с exponential backoff и джиттером.
- Ограничение частоты реконнектов (чтобы не попадать под server rate limit).

### 8.3 Настройки фильтрации

- Пользователь может настроить фильтры локально.
- Принцип: **сервер не обязан знать фильтры** (фильтрация на клиенте), но сервер может позже поддержать серверные подписки.

Пример групп фильтрации (структуру можно менять):

- по `blockchain` (sol/bsc)
- по диапазонам `dev_holds_percent`, `snipers_hold_percent`
- по наличию ссылок (`telegram`, `twitter`, `website`)
- по протоколу (`protocol`)
- whitelist/blacklist по `dev_wallet`, `token_address`

### 8.4 Автооткрытие ссылок

- Настройка `auto_open` (вкл/выкл)
- Лимиты:
  - не больше X открытий/мин
  - анти-дубликаты (не открывать один и тот же `token_address` чаще, чем раз в Y минут)
- При автооткрытии — открывать приоритетную ссылку (правило выбора фиксируется: например website → twitter → telegram).

## 9) Token Feed: источники как “плагины” (как в текущем коде)

### 9.1 Принцип расширяемости

Цель: иметь возможность добавлять новые источники (например `gmgn_api`) и/или комбинировать их, **не меняя** код клиента и минимально затрагивая WSS слой.

Текущая удачная основа:

- `TokenFeedPreparer` (protocol) задаёт контракт:
  - `prepare_token_feed(raw_event) -> Optional[TokenFeedBase]`
  - `set_callback(callback)`
- `TokenFeedCollector` получает список preparers и прогоняет каждое входящее событие через них.

### 9.2 Требования к новому источнику (пример: GMGN)

Новый источник обязан:

- предоставлять класс, совместимый с `TokenFeedPreparer`
- преобразовывать свой raw payload к `TokenFeedBase`
- регистрировать callback так, чтобы collector мог получать события

Идея комбинирования:

- 1 collector может держать список: `[AxiomDevTokenData, GmgnTokenData, ...]`
- каждый preparer решает сам: “это мой формат/мой room/мой payload?” → если да, возвращает `TokenFeedBase`, иначе `None`.

### 9.3 Нормализация данных

Единый формат `TokenFeedBase` является контрактом к WSS клиентам. Поэтому:

- все preparers должны приводить данные к единой схеме
- при несовпадении данных (например, у одного источника нет `snipers_hold_percent`) — допускаются `Optional` поля и документируется, какие источники заполняют что.

## 10) Наблюдаемость (метрики/логи)

Минимально:

- кол-во активных WSS соединений
- кол-во соединений по ключам (top keys)
- отказов авторизации по причинам (invalid/expired/revoked/rate_limited)
- скорость доставки событий (events/sec)
- задержка (если возможно измерять)

## 11) Предлагаемая структура `src/` (не ломая текущую)

Текущая серверная часть уже в `src/server/...`. Предлагается добавить рядом клиент:

- `src/server/`
  - `app/`
    - `services/token_feed/` (оставить и развивать текущую архитектуру)
    - `schemas/` (контрактные модели для token feed и API)
    - `api/` (HTTP endpoints)
    - `ws/` (WSS endpoints + connection manager)
    - `auth/` (api key validation, rate limiting интеграция)
    - `admin/` (эндпоинты управления ключами)
  - `third_party_apis/` (уже есть)
- `src/client/`
  - `apps/desktop/` (Tauri/Electron проект)
  - `packages/shared/` (если понадобится shared схемы/типы)

Важно: это **организационное** предложение. Реальные папки можно вводить постепенно, не ломая текущий код.

## 12) Definition of Done (критерии готовности v1)

Сервер:

- можно создать/отозвать/продлить ключ
- клиент с валидным ключом подключается по WSS и получает `token_feed` события
- при истечении/отзыве — клиент отключается с понятной причиной
- включён rate limiting на validate и ws connect

Клиент:

- ввод ключа, сохранение, статус подключения
- фильтрация событий по настройкам
- автооткрытие ссылок с лимитами и анти-дубликатами
