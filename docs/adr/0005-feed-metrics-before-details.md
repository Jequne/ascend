# 0005. Показатели token feed перед дополнительными данными

- Статус: `accepted`
- Дата: `2026-09-28`
- Участники: разработчики Ascend

## Контекст

Клиент принимает и автооткрывает токен после проверки локальных фильтров.
Сервер ожидал одновременно fees и сведения прошлых пар, причём оба запроса
попадали в фоновую очередь. Медленные изображения и ссылки задерживали даже
стратегию `Last Tokens`, для которой достаточно ATH из истории кошелька.
Агент назначался до ожидания очереди и мог использовать уже охлаждённый маршрут.

## Решение

Контракт подготовки обновлений предоставляет асинхронные последовательности.
Collector отправляет каждое обновление сразу, сохраняя независимость developer
и funding потоков и отмену при остановке. Developer сначала передаёт ATH и
счётчики, затем fees. Funding передаёт проверенные fees и счётчики. Изображения
и ссылки досылаются после показателей. Формат WebSocket остаётся совместимым.

История кошелька, поиск funder и fees приоритетны; дополнительные данные фоновые.
Developer и funding используют общий кэш по кошельку и паре. Общий ограничитель
частоты сохраняется. Агент выбирается непосредственно перед HTTP-вызовом.
`429` охлаждает весь proxy-маршрут по `Retry-After` и увеличивает интервал его
последующих запросов; успешные ответы постепенно восстанавливают частоту.

## Последствия

`Last Tokens` может открыть токен до получения fees, остальные стратегии после
проверки нужных показателей. Клиент обновляет ту же карточку и не повторяет
автооткрытие. Карточка некоторое время может содержать неполные дополнительные
данные. Количество сообщений увеличивается, дополнительные HTTP-запросы для
раннего обновления не нужны. Неизвестные лимиты Axiom не позволяют гарантировать
полное отсутствие `429` или фиксированное время появления карточки.

Регрессионные тесты задерживают fees и сведения пар независимо, проверяют
приоритеты, объединение запросов, раннее открытие и отсутствие повторного
открытия. SDK-тесты проверяют очередь во время `429` и восстановление частоты.

## Альтернативы

Уменьшение общего интервала запросов повышает нагрузку на Axiom и риск `429`.
Ожидание полного набора данных сохраняет задержку по необязательным сведениям.
Открытие до проверки показателей нарушает пользовательские фильтры.
