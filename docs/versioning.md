# Версионирование

## Единицы выпуска

Ascend не имеет общей версии репозитория. Версия назначается независимо каждой
части, которую можно собрать и выпустить отдельно.

| Часть                 | Текущий источник версии                                       | Git-тег                        |
| --------------------- | ------------------------------------------------------------- | ------------------------------ |
| Desktop-клиент        | `src/client/package.json`, синхронизированный с Tauri и Cargo | `client-vMAJOR.MINOR.PATCH`    |
| Браузерное расширение | `src/extension/package.json`                                  | `extension-vMAJOR.MINOR.PATCH` |
| Серверный deployment  | `src/server/VERSION`                                          | `server-vMAJOR.MINOR.PATCH`    |

Версии разных частей не обязаны совпадать. Тег ставится на commit, из которого
собран соответствующий артефакт. Один commit может иметь несколько тегов, если
из него одновременно выпускается несколько частей.

Все части используют [Semantic Versioning](https://semver.org/lang/ru/) в форме
`MAJOR.MINOR.PATCH` без префикса `v` в файлах версий:

- `MAJOR` — несовместимое изменение публичного поведения или контракта;
- `MINOR` — обратно совместимая возможность;
- `PATCH` — обратно совместимое исправление или внутреннее изменение.

До версии `1.0.0` несовместимое изменение повышает `MINOR`, а исправление —
`PATCH`. Версия меняется только у затронутой единицы выпуска.

## Desktop-клиент

Версия клиента дублируется там, где ее требуют инструменты сборки:

- `src/client/package.json` и корневая запись `src/client/package-lock.json`;
- `src/client/src-tauri/tauri.conf.json`;
- секция `[package]` в `src/client/src-tauri/Cargo.toml` и запись пакета клиента
  в `Cargo.lock`.

Перед выпуском обновите эти значения и выполните из `src/client`:

```powershell
npm run version:check
npm run format:check
npm run lint
npm run check
npm run test
npm run build
```

После проверок соберите Tauri bundle и создайте тег, например
`client-v0.2.0`. Release notes должны описывать пользовательские изменения,
миграции настроек и известные ограничения.

Расширение, вложенное в Tauri bundle, сохраняет собственную версию из своего
`manifest.json`. Если в выпуск клиента включена новая сборка расширения, нужно
повысить обе версии: расширения — из-за его изменений, клиента — из-за изменения
содержимого клиентского артефакта.

## Браузерное расширение

Версия задается в `src/extension/package.json`; WXT переносит ее в
`manifest.json` собранного расширения. Обновляйте package-файлы командой из
`src/extension`:

```powershell
npm version 0.2.0 --no-git-tag-version
npm run version:check
npm run format:check
npm run lint
npm run check
npm run test
npm run build
npm run test:e2e
```

Замените `0.2.0` требуемой версией. После проверок создайте тег вида
`extension-v0.2.0`. Не используйте обычный npm-тег `v0.2.0`: в общем
репозитории он не показывает, к какой части относится выпуск.

## Совместимость клиента и расширения

Версии продуктов не определяют их совместимость. Клиент `0.x` может работать с
расширением `1.x`, если они поддерживают одну версию bridge-протокола.

Версия bridge-протокола хранится отдельно в реализациях клиента и расширения.
Обратно совместимые добавления не меняют ее. При несовместимом изменении:

1. увеличьте версию протокола в обеих реализациях;
2. добавьте тесты успешного обмена и отказа для старой версии;
3. повысьте версии клиента и расширения по их собственным правилам;
4. укажите минимально совместимые выпуски в release notes обеих частей.

## Сервер

Сервер версионируется как развертываемый артефакт, а не как набор внутренних
модулей. Пока приложение развертывается целиком, ему достаточно одной версии в
`src/server/VERSION` и тега `server-vMAJOR.MINOR.PATCH`. Изменение языка,
рефакторинг или замена внутреннего модуля сами по себе не требуют `MAJOR`, если
внешние контракты остаются совместимыми.

Версии внешних контрактов — HTTP API, WebSocket messages и схем данных — не
следует связывать с версией deployment. Для несовместимого изменения контракт
получает собственную версию в URL или сообщении и, по возможности, период
совместной поддержки старой и новой версии. До появления такой версии
несовместимое изменение выпускается согласованно с потребителями и явно
описывается в release notes.

Если часть сервера в будущем станет независимо развертываемым сервисом, только
тогда она получает собственный файл `VERSION`, image tag и Git-тег вида
`<service>-vMAJOR.MINOR.PATCH`. Библиотека или модуль без самостоятельного
артефакта и жизненного цикла отдельной версии не получает.

Server image следует публиковать с неизменяемым тегом версии, например
`server:0.2.0`, и при необходимости дополнительным тегом с commit SHA. Тег
`latest` не используется как единственная ссылка для production-развертывания.

## Общий порядок выпуска

1. Определите затронутые единицы выпуска и тип повышения для каждой.
2. Обновите их источники версий и release notes.
3. Выполните проверки из [руководства разработчика](development.md).
4. Соберите артефакты из отмечаемого commit и проверьте содержащиеся в них
   версии.
5. Создайте component-specific Git-теги и опубликуйте неизменяемые артефакты.
6. Для server deployment сохраните предыдущие версии и выполните процедуру из
   [руководства развертывания](deployment.md).
